# Платежи после сделки

Инструмент для проверки сделок должников: загружаете кредитный отчёт ОКБ
(«Кредистория») в PDF, указываете дату сделки — получаете сумму и полный
перечень платежей, внесённых после этой даты, с разбивкой по кредиторам и
договорам.

> В репозитории два инструмента, которые собираются одной командой и работают
> по одним правилам — офлайн, без сервера, без отправки данных куда-либо:
>
> * **«Платежи после сделки»** — `dist/index.html`, описан ниже;
> * **«Конструктор заявлений»** — `dist/statement/index.html`, сборка заявлений
>   об оспаривании сделок должника. См. раздел
>   [«Конструктор заявлений»](#конструктор-заявлений-об-оспаривании-сделок).

## Как пользоваться

Открыть `dist/Платежи после сделки.html` двойным кликом. Всё.

Файл самодостаточный: pdf.js и парсер встроены внутрь. Ни сервера, ни
интернета не требуется. **PDF никуда не отправляется** — отчёт разбирается
в браузере на вашем компьютере, поэтому паспортные данные и ФИО должника
не покидают устройство.

Файл можно скопировать на флешку, переслать коллеге, положить на рабочий
стол — он останется работоспособным.

## Что показывает

* **Сумма и количество платежей после даты сделки** — с группировкой по
  кредиторам, внутри — по договорам, внутри — построчный список платежей
  с разбивкой на основной долг, проценты и пени.
* **График по месяцам** за всю историю: видно контраст «до сделки / после».
* **Договоры, заключённые после сделки** — по полю «Дата совершения сделки».
* **Договоры без данных о платежах** — важный раздел: по ним кредитор не
  передал в бюро построчный список, и отсутствие платежей там ничего не
  доказывает.
* **Проверка разбора** — сверка с контрольными суммами самого отчёта.

Фильтры: строго после даты сделки или включая её; верхняя граница периода;
действующие/закрытые договоры; скрытие нулевых платежей и порог минимальной
суммы (отсекает копеечные технические списания).

Отдельно — **«Не считать договоры, заключённые после сделки»**: кредиты,
взятые уже после, к прежним обязательствам не относятся. Договор считается
новым по полю «Дата совершения сделки»; договоры без даты остаются в расчёте.
Отсечённая сумма показывается явно, а не пропадает молча.

## Перекрёстная проверка по задолженности

Раздел «Сведения о сумме задолженности» — история снимков долга с датами.
Сумма снижений основного долга между снимками даёт независимую оценку того,
сколько долга погашено: она не опирается ни на таблицу платежей, ни на
агрегат отчёта.

Оценка проверена: по договору с СОВКОМБАНКом она дала 91 151,35 ₽ — ровно
столько, сколько сам отчёт указывает в поле «По основному долгу».

Главная польза — договоры, по которым построчного списка платежей нет вовсе.
В отчёте на 106 страниц таких десять, и для четырёх из них история долга
показывает погашение (89 788 ₽, 71 430 ₽, 101 138 ₽, 3 308 ₽) там, где раньше
не было видно ничего.

Это **оценка снизу и косвенная**: она не включает платежи по процентам и
пеням, а снижение долга бывает вызвано не платежом, а списанием,
переуступкой или реструктуризацией. Поэтому в расчёт она не входит — только
показывается как повод запросить первичные документы.

Можно задать несколько дат сделок — появится сводная таблица для сравнения.

Кнопка «Печать / PDF» печатает развёрнутый отчёт по всем разделам сразу,
без интерфейсных элементов — пригодно для приложения к заключению.

## Ввод даты

Поле принимает `13.12.2021`, `13122021` (точки подставляются сами),
`2021-12-13` и `13 декабря 2021` — последние два можно просто вставить из
документа. Рядом кнопка календаря. Несуществующие даты вроде 31 февраля
подсвечиваются сразу.

Нативное `<input type="date">` здесь не используется намеренно: оно считает
дату готовой после первой же цифры года, что при перерисовке сбрасывало
позицию ввода и не давало дописать год.

## Сессии и выгрузка

* **Сохранить сессию** — файл `.json` с разобранным отчётом, датами сделок и
  фильтрами. Открывается мгновенно, без повторного разбора PDF (~30 КБ).
  **Файл сессии содержит персональные данные должника** — храните его там же,
  где материалы дела.
* **Выгрузить CSV** — все платежи текущего расчёта, разделитель `;` и BOM,
  русский Excel открывает без «Мастера импорта».
* В `localStorage` сохраняются только настройки фильтров. Персональные данные
  туда не пишутся: на `file://` это хранилище общее для всех локальных страниц.

## Размещение в сети

`dist/index.html` и `dist/statement/index.html` намеренно закоммичены — это
позволяет разворачивать сайт без сборки на стороне хостинга. Анализатор
отчётов оказывается в корне, конструктор заявлений — по адресу `/statement/`.

Render: **New → Static Site**, подключить репозиторий, Publish Directory —
`dist`, Build Command оставить пустым. Настройки уже описаны в `render.yaml`.

Размещение безопасно: обе страницы полностью клиентские. PDF обрабатывается в
браузере посетителя, дела и реквизиты хранятся в его же `localStorage` — на
сервер не попадает ни то, ни другое.

## Старый формат отчёта (до v2)

Отчёты v1.x устроены иначе, и разбор для них отдельный — ветка выбирается по
версии из колонтитула.

* Таблица платежей свёрстана **колонками**: значения идут сверху вниз
  (сумма → основной долг → проценты → иное → дата), причём строки «плавают» —
  у длинных чисел «(%)» переносится на следующую строку. Разбор идёт по
  колонкам, а не по строкам.
* **Статус платежа нарисован иконкой** и в тексте отсутствует. Он читается из
  графического слоя, а соответствие «цвет → статус» берётся из легенды над той
  же таблицей — палитра нигде не зашита.

По умолчанию засчитываются только статусы, при которых деньги поступили
(«Оплачен вовремя», «Оплачен не вовремя» и оба частичных). Остальные видны в
интерфейсе с суммой и отдельной пометкой, набором статусов можно управлять.

«Платёж не наступил» и «Нет данных» помечены одинаково-серым и неразличимы —
они объединены в один статус. Оба означают отсутствие платежа, на расчёт это
не влияет.

## Важно про данные ОКБ

Отчёт содержит два независимых источника цифр по каждому договору:
агрегат «Сумма всех внесенных платежей» и построчную таблицу «Фактические
платежи по договору». Кредиторы передают их отдельно, и **они регулярно не
сходятся**. В проверенном отчёте на 106 страниц расходятся 9 договоров из 10;
в одном случае агрегат равен 0 ₽ при 12 фактических платежах по 5 260 ₽.

Инструмент считает по построчной таблице (это единственный источник дат) и
показывает все расхождения на вкладке «Проверка разбора». Договоры с
расхождением стоит проверять по первичным документам — там список платежей
может быть неполным.

## Оформление

Плиточная раскладка: размер плитки задаёт важность. Цвет несёт смысл, а не
украшает — ирис отмечает период после сделки, шкала «в срок → просрочка свыше
90 дней» показывает платёжную дисциплину месяца, кирпичный означает проблему
с данными. Зелёный нигде не используется как элемент интерфейса, только как
крайняя точка этой шкалы.

Шрифт — **Onest** (SIL Open Font License 1.1), встроен в сборку как data:-URI.
Ссылка на CDN тут не годится: приложение должно работать с флешки без
интернета, и шрифт молча отвалился бы вместе со всей типографикой.

# Конструктор заявлений об оспаривании сделок

Второй инструмент репозитория: `dist/statement/index.html` (или
`dist/Конструктор заявлений.html` — тот же файл с человеческим именем для
двойного клика).

Задача — сократить время подготовки заявления об оспаривании сделки должника
за счёт структурированного ввода данных и автоматической сборки документа из
юридических блоков. **Никакого ИИ и никакой автоматической юридической
квалификации:** какие обстоятельства есть в деле и какие блоки включать,
решает человек. Приложение отвечает за рутину — подстановку реквизитов,
условные поля, порядок разделов, нумерацию приложений и выгрузку.

## Путь пользователя

```text
Новое дело → реквизиты → сделка → тип объекта → стороны →
несколько вопросов → выбор блоков → готовое заявление → DOCX / PDF
```

Одни и те же данные вводятся **один раз**. Реквизиты дела и должника
подставляются во все заявления внутри дела, контрагент выбирается из
участников дела, а не набирается заново.

## Что внутри

* **Дела.** Суд, номер, процедура, дата возбуждения, судебный акт, должник,
  арбитражный управляющий. Пустые поля управляющего берутся из профиля.
* **Стороны.** Юридическое лицо, физическое лицо, ИП — у каждого свой набор
  полей. Сторона заводится один раз и переиспользуется в сделках дела.
* **Сделки.** Тип, даты, номер, сумма, предмет, объект, исполнение,
  обстоятельства, документы. Форма динамическая: поля объекта зависят от того,
  недвижимость это, транспорт, деньги или иное; вопрос о встречном исполнении
  раскрывает разные наборы полей для «частично» и «нет».
* **Обстоятельства.** Пять вопросов «да / нет» (неравноценность, вред
  кредиторам, заинтересованность, предпочтение, осведомлённость). Ответ «да»
  включает соответствующий блок заявления и открывает уточняющие поля,
  «нет» — выключает блок.
* **Конструктор.** Слева список блоков: включить, выключить, перетащить,
  раскрыть и отредактировать текст. Справа — предпросмотр, который
  перестраивается на каждое изменение. Незаполненные переменные подсвечены
  прямо в тексте.
* **Проверка.** Обязательные поля и логические ошибки: дата исполнения раньше
  даты договора, сумма сделки расходится с суммой платежа, включён блок
  неравноценности без стоимостей встречного исполнения.
* **Приложения.** Список собирается из документов сделки, нумерация
  пересчитывается при любом изменении.
* **Версии.** Снимок состава блоков и текста; версии можно смотреть,
  восстанавливать и сравнивать построчно.
* **Копирование сделки.** «Создать на основе этой сделки» переносит стороны,
  тип, обстоятельства и состав блоков — меняются только номер и даты.

## Шаблоны и переменные

Текст не захардкожен в интерфейсе. Каждый блок — это шаблон с переменными
вида `{{DEAL_DATE}}`, `{{DEBTOR_NAME}}`, `{{OBJECT_ADDRESS}}`. Реестр
переменных единый, кнопка «Вставить переменную» берёт список из него же.

```text
{{DEAL_DATE}} между {{DEBTOR_SHORT}} и {{COUNTERPARTY_SHORT}}
заключён {{DEAL_TYPE}} № {{DEAL_NUMBER}}.

  ↓

15 апреля 2025 года между ООО «Ромашка» и ООО «Василёк»
заключён договор купли-продажи № 15.
```

Суммы попадают в документ и цифрами, и прописью: `{{DEAL_AMOUNT}}` даёт
`8 400 000,00`, `{{DEAL_AMOUNT_WORDS}}` — «Восемь миллионов четыреста тысяч
рублей 00 копеек». Падежи статуса управляющего («конкурсный управляющий» /
«конкурсным управляющим») хранятся в справочнике, а не выводятся правилами:
склонение по правилам в русском языке всё равно даёт осечки.

Условие показа блока записывается человекочитаемо:

```text
deal.unequal = true
deal.objectType = money AND deal.amount > 1000000
```

Разбирает их собственный мини-интерпретатор — сравнения, склеенные `AND` и
`OR`. `eval` не используется: выражение приходит из редактируемого шаблона,
исполнять оттуда код незачем.

Библиотека блоков правится в интерфейсе: у стандартных блоков меняется текст,
свои блоки создаются целиком. Правка текста прямо в конструкторе действует
только на одно заявление и библиотеку не трогает.

## Выгрузка

* **DOCX** собирается вручную, без библиотек: `.docx` — это ZIP из нескольких
  XML-файлов, и написать их дешевле, чем тащить в офлайновую страницу мегабайт
  стороннего кода. Поля по ГОСТ Р 7.0.97 (слева 30 мм), Times New Roman 14 пт,
  полуторный интервал, номера страниц полем `PAGE`.
* **PDF** — печатью. Листы A4 раскладываются по фактическим высотам абзацев
  (браузер измеряет каждый), поэтому в предпросмотре и в файле одно и то же
  разбиение и одинаковые номера страниц.

## Где хранятся данные

В `localStorage` браузера, на этом компьютере. Сервера у приложения нет —
как и у анализатора отчётов. Кнопка «Резервная копия» выгружает всё в JSON и
загружает обратно: так дела переносятся на другую машину и переживают чистку
кэша.

Файлы документов **не загружаются**: приложение хранит только реквизиты
(тип, номер, дата, примечание). Список приложений от этого собирается ничуть
не хуже, а персональные данные не оседают в хранилище браузера.

## Чего в первой версии нет

Регистрации и входа — приложение локальное, «профиль» это просто реквизиты
управляющего для подстановки. Загрузки файлов, массового импорта сделок из
Excel и общей библиотеки шаблонов организации: всё это требует сервера,
которого здесь сознательно нет.

## Разработка

```bash
npm install
node tools/fetch-font.mjs                      # один раз: скачать и встроить Onest
npm run build                                  # пересобрать оба приложения в dist/
node test/run.mjs отчёт1.pdf отчёт2.pdf        # прогнать парсер по реальным PDF
npm run test:statement                         # стенд конструктора заявлений
```

`src/fonts/onest.css` в репозиторий не коммитится — его создаёт `fetch-font`.
Без него сборка остановится с понятной ошибкой.

* `src/parser.js` — разбор PDF. Не зависит ни от DOM, ни от файловой системы:
  один и тот же код работает в браузере и в Node-тестах.
* `src/app.html` — интерфейс. Метки `@@PARSER@@`, `@@PDFJS@@`,
  `@@PDFJS_WORKER@@` заменяются при сборке на встроенные скрипты.
* `build.mjs` — сборка в один файл. Экспорты pdf.js вытаскиваются в
  `globalThis` разбором финального `export{...}` бандла, поэтому обновление
  pdf.js не требует правок. `globalThis.pdfjsWorker` заставляет pdf.js
  работать в главном потоке — из `file://` отдельный worker-файл загрузить
  нельзя.
* `test/run.mjs` — сверяет разобранные суммы с контрольными из отчёта.
  Падением считается только сбой разбора (обрыв таблицы, нераспознанная
  сумма); расхождение агрегата со списком — особенность данных ОКБ.
* `test/selftest-build.mjs` — собирает копию приложения со встроенным PDF,
  чтобы прогнать весь путь прямо из `file://`.

Парсер проверен на форматах отчёта **v3.8.2.0** и **v3.19.0.0**.

Конструктор заявлений собирается из `src/statement/`:

* `data.js` — справочники, реестр переменных и библиотека блоков. Ни разметки,
  ни логики интерфейса: только данные.
* `store.js` — модель, шаблонизатор, условия, правила проверки, версии.
  Про DOM не знает — тот же код исполняется в Node-тесте.
* `doc.js` — ZIP и XML для DOCX, раскладка листов A4 для печати.
* `app.html` / `app.js` — интерфейс. Метки `@@DATA@@`, `@@STORE@@`, `@@DOC@@`,
  `@@APP@@` заменяются при сборке на встроенные скрипты.
* `test/statement.mjs` — стенд конструктора: подстановка переменных, условия
  блоков, нумерация приложений, правила проверки, сравнение версий и структура
  собранного DOCX (ZIP разбирается обратно, CRC сверяется, XML проверяется на
  сбалансированность). Отдельно сверяются метрики листа и скрытого контейнера
  для замера — если они разойдутся, текст молча полезет за обрез страницы.
